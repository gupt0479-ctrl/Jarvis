## Detailed Changes
Four root problems, fixed in order. Fixes 1–3 are mechanics (P1 below); Fixes 4–5 are content/routing (P2 below).

### Fix 1 — Control tokens must never reach the screen
The model is emitting its *actions* as text and the UI prints them. Every one of these must be parsed out, executed as a real action, and stripped from the visible message: `{ "tool": "showProject", "arguments": {...} }`, `<lookupFact query="..." />`, `<orbyMessage>...</orbyMessage>`, `<details>...</details>`, and the `Navigation:` / `Project details:` fenced-JSON blocks.
- **Primary fix:** use real **function/tool calling** so the providers return directives as structured `tool_calls`, not text in the content. Azure OpenAI and the OpenAI-compatible backups all support this.
- **Backstop sanitizer (required):** because free models sometimes ignore tool-calling and inline JSON anyway, the route also runs a sanitizer that (a) extracts any `tool`/`navigate`/`orbyMessage`/`<details>`/`lookupFact` payloads, (b) uses them to drive navigation + card + Orby speech, and (c) deletes them from `displayText`. After sanitizing, `displayText` contains **zero** raw JSON, tags, or `Navigation:`/`Project details:` blocks.
- **The `/api/chat` response shape is fixed:** `{ displayText, orbyMessage, navigate: { sectionId, itemSlug?, itemIndex? }, card?: { type, data } }`. The frontend renders `displayText` as markdown prose, the `card` as the evidence-card component **below** the prose, sends `orbyMessage` to Orby, and runs `navigate`.

### Fix 2 — Orby speaks and returns home on every send
Orby is currently silent. The `orbyMessage` (AI-generated per prompt, in persona voice, grounded, length-capped) is the line Orby must say — it was leaking as `<orbyMessage>` text instead of driving the character. On every send: Orby glides back to its **home position next to the portfolio button**, the page scrolls to the target, and Orby pops `orbyMessage` on arrival. `orbyMessage` goes to the speech cloud only — never into `displayText`.

### Fix 3 — Deterministic navigation for the fixed prompts (kill the BOOM-default)
Almost everything renders BOOM because the model is left to guess the target. For the 16 known fixed prompts, navigation is **not** the model's job — it's read from an author-specified `navTarget` (section + specific item). So "weirdest thing" deterministically opens the TradingView project, "highest-impact" opens Jarvis, etc. Item-level navigation: `navigate` carries an optional `itemSlug`/`itemIndex`; `ProjectsSlider` centers that project; the experience section scrolls to that card.

Each fixed prompt gets `{ navTarget, answerBrief }`. The brief **guides** the model's content (it is not rendered verbatim) and the answer is cached (token optimization). Resolve the real Sanity slugs for each named item.

### Fix 5 — Free-typed routing (read everything, don't default to BOOM)
For questions that are **not** one of the 16 fixed prompts, instruct the model to read the **whole catalog** before choosing a section and to pick the item that best matches the question — explicitly do not default to BOOM. Grounding + refusal rules unchanged.

### Token-optimization update
The 16 fixed prompts now carry author-written answer briefs + deterministic nav. Cache the rendered answer per `(persona, promptId)` so repeat clicks cost zero model calls, and skip the model's section-routing step entirely for fixed prompts (navTarget is known). Free-typed questions still go live through the Azure→free chain.
