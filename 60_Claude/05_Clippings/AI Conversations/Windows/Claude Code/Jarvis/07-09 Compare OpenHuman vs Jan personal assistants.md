## OpenHuman vs Jan — researched conclusion

**Bottom line up front: don't switch to OpenHuman. Keep Jan for local model chat, and if you want an actual "knows me" assistant, build the memory layer on top of what you already have (this Jarvis vault + Claude Code), not on a 5-month-old app with unaudited broad OAuth access.**

### Why "is OpenHuman better since it stores memory like Obsidian" is the wrong frame

It's true — OpenHuman's Memory Tree really does write plain Markdown into an Obsidian-compatible vault, inspired explicitly by [Karpathy's "LLM wiki" concept](https://x.com/karpathy/status/2039805659525644595). That part is real and well-built. But you're not evaluating it in a vacuum — **you already have that.** This Jarvis vault is Obsidian + Claude Code + MCP tools (`vault_read/write/patch`, Gmail, Google Calendar MCP servers are literally already in your toolset) + a memory system (`60_Claude/07_AI_Information/`, session logs, skills like `/startday`/`/closeday`) + orchestration via skills and subagents. OpenHuman is trying to automate, for a stranger, the exact system you've already hand-built and control end-to-end. The one thing it has that you don't is **automatic 20-minute polling ingestion** from connected accounts — everything else (Markdown memory, agent orchestration, MCP integrations) you already have, minus the OAuth aggregation risk and the subscription.

### How you'd actually use either one day-to-day

- **Jan**: download a GGUF model (Jan-Code-4B, Qwen, Llama, Gemma) through its Hub, chat locally, optionally bridge to Claude/GPT when you want frontier quality, optionally run `jan launch claude` to point Claude Code at a local model instead of Anthropic's API for privacy-sensitive coding. That's it — it's a model runner, not an assistant that remembers your life.
- **OpenHuman**: install, sign in to their hosted account, grant OAuth to Gmail/Calendar/etc., let auto-fetch build your Memory Tree, then talk to the mascot for briefings ("what's waiting on me") and let the subconscious loop work in the background. This only becomes useful once you've handed it broad account access — there's no meaningful lightweight mode.

### Local models that work with each

- **Jan**: native — llama.cpp backend, Hub UI for HuggingFace GGUF downloads, own Jan-v3-4B/Jan-Code-4B models tuned for consumer hardware, OpenAI-compatible server at `localhost:1337`.
- **OpenHuman**: Ollama or LM Studio, opt-in per workload, `gemma3:1b-it-qat` / `all-minilm` defaults for embeddings+summarization; full local chat/reasoning requires manually setting provider strings — not the default experience despite "local-first" marketing.

### What I'd actually do

1. **Keep Jan** for what it's good at — local/private chat and as a local backend for Claude Code when you want zero-cloud coding sessions.
2. **Don't hand OpenHuman simultaneous OAuth to email/calendar/code/payments yet.** It's 5 months old, has no independent security audit, ships via curl-pipe install on macOS/Linux, and monetizes through its own account system — the risk/access ratio is bad for a primary machine right now. If you're curious, try it in a throwaway Google account, read the install script first, and see if the Memory Tree quality is even good before trusting it with real accounts.
3. **The actual gap worth closing** is auto-ingestion. You already have `mcp__claude_ai_Gmail__*` and `mcp__claude_ai_Google_Calendar__*` tools wired into this session. A cheap, fully-controlled version of OpenHuman's "auto-fetch" is: a scheduled skill (via `/loop` or cron) that periodically pulls recent email/calendar into a memory note in this vault, using tools you already trust — same payoff (proactive context), none of the third-party aggregation risk.
4. If you want a more automated memory layer without building it yourself, **Khoj** (self-hosted, native Obsidian plugin, been around since 2021, doesn't need simultaneous OAuth to your whole life) is a meaningfully lower-risk middle ground worth a look before OpenHuman.

# What is OpenHuman?

OpenHuman is three things most assistants aren't: **a brain** that builds a persistent, local memory of your world; **a fantastic orchestrator** that runs fleets of agents on durable graphs; and **a deep researcher** that sweeps your data and the web before you finish asking. Every bullet links to the deeper writeup in the [docs](https://tinyhumans.gitbook.io/openhuman/).

### 🧠 The brain

- **[Memory Tree](https://tinyhumans.gitbook.io/openhuman/features/memory-tree) + [Obsidian Wiki](https://tinyhumans.gitbook.io/openhuman/features/obsidian-wiki)**: your data compressed into scored Markdown trees in SQLite on your machine, mirrored as an [Obsidian vault](https://x.com/karpathy/status/2039805659525644595) you can open and edit. No vector-soup black box.
- **[100+ OAuth integrations, 5,000+ MCP servers, 90,000+ Skills](https://tinyhumans.gitbook.io/openhuman/features/integrations)**: one click into Gmail, Notion, GitHub, Slack and the rest of your stack. [Auto-fetch](https://tinyhumans.gitbook.io/openhuman/features/obsidian-wiki/auto-fetch) feeds the brain every 20 minutes, so it has tomorrow's context this morning.
- **[A subconscious](https://tinyhumans.gitbook.io/openhuman/features/subconscious)**: a background loop that diffs your world, advances your goals, and writes your morning briefing. Thinking continues after you stop typing.
- **[Goals & Todos](https://tinyhumans.gitbook.io/openhuman/features/goals-and-todos)**: long-term goals, durable per-thread goals, and a shared kanban board per conversation.
- **[TokenJuice](https://tinyhumans.gitbook.io/openhuman/features/token-compression)**: tool output compressed before it hits the model: same information, up to 80% fewer tokens. A brain this big would be unaffordable without it.

### 🕸️ The orchestrator

- **[Workflows](https://tinyhumans.gitbook.io/openhuman/features/workflows)**: the agent proposes the automation; you review it on a canvas and save. Durable, trigger-driven, approval-gated runs on open-source [tinyflows](https://github.com/tinyhumansai/tinyflows).
- **[A harness that finishes the job](https://tinyhumans.gitbook.io/openhuman/developing/architecture/agent-harness)**: checkpointed graph runs on open-source [tinyagents](https://github.com/tinyhumansai/tinyagents). Stuck agents get steered, halted ones return a root cause, and every run replays with real per-call costs.
- **[A split brain, always on](https://tinyhumans.gitbook.io/openhuman/features/orchestration)**: a fast reflex agent triages inbound traffic while a deep reasoning core delegates to worker fleets, steered by the subconscious.
- **[An agent economy](https://tinyhumans.gitbook.io/openhuman/features/tinyplace)**: a `@handle` on [tiny.place](https://tiny.place), Signal-encrypted agent-to-agent orchestration, x402 USDC bounties and trading. Keys never touch disk.

### 🔬 The deep researcher & doer

- **[SuperContext](https://tinyhumans.gitbook.io/openhuman/features/super-context)**: a research scout sweeps your memory and files before the model reads your first message. No cold starts.
- **Batteries included**: web search, scraper, coder toolset, a real [browser](https://tinyhumans.gitbook.io/openhuman/features/native-tools/browser-and-computer), and [native voice](gitbooks/features/native-tools/voice.md) with in-process Whisper. [Model routing](https://tinyhumans.gitbook.io/openhuman/features/model-routing) picks the right LLM per workload on one subscription, with [local AI optional](https://tinyhumans.gitbook.io/openhuman/features/model-routing/local-ai).
- **[Meeting agents](https://tinyhumans.gitbook.io/openhuman/features/mascot/meeting-agents)**: joins **Meet, Zoom, Teams, and Webex** with a face and a voice. It auto-joins from your calendar, streams a live transcript, answers by name, and files a summary with action items.
- **[Image & video generation](https://tinyhumans.gitbook.io/openhuman/features/native-tools)**: Seedream/SeedEdit images and Seedance/Veo video, straight into your workspace on the same subscription.
- **[17 messaging channels](https://tinyhumans.gitbook.io/openhuman/features/channels)**: Telegram, Discord, Slack, WhatsApp, Signal, iMessage… plus **native email** (IMAP IDLE + SMTP). Your agent reaches you where you already are.

### 🧍 Human, private, yours

- **Simple, UI-first & Human**: install to working agent in a few clicks, with no config files and no terminal. And it has [a face](https://tinyhumans.gitbook.io/openhuman/features/mascot): a mascot that speaks, reacts, and remembers you.
- **[Privacy & security](https://tinyhumans.gitbook.io/openhuman/features/privacy-and-security)**: on-device encrypted data, approval gate, OS-keyring secrets, and opt-in sandboxing. There is also **[Privacy Mode](https://tinyhumans.gitbook.io/openhuman/features/privacy-mode)**: flip one switch and no inference leaves your machine, enforced in the Rust core.
- **[Themes & Theme Studio](https://tinyhumans.gitbook.io/openhuman/features/theming)**: five theme families plus a full visual editor, exportable as JSON.

## Context in minutes, not weeks

OpenHuman is the first agent harness that gets to know you in minutes. Inspired by [Karpathy's LLM Knowledgebase](https://x.com/karpathy/status/2039805659525644595). Most agents start cold. Hermes learns by watching you work; OpenClaw waits for plugins to ferry context in. Either way, you spend days or weeks before the agent knows enough about your stack to be genuinely useful.

 <img src="./gitbooks/.gitbook/assets/memory.png" alt="OpenHuman context-building diagram">
</p>

> OpenHuman summarizes and compresses all your documents, emails & chats; and creates a memory graph that lets your agent remember everything about you.

OpenHuman skips the wait. Connect your accounts, let [auto-fetch](https://tinyhumans.gitbook.io/openhuman/features/integrations/auto-fetch) pull data locally on a 20-minute loop, and then have [Memory Trees](https://tinyhumans.gitbook.io/openhuman/features/memory-tree) compress everything into Markdown files stored intelligently in a [Karpathy-style Obsidian wiki](https://tinyhumans.gitbook.io/openhuman/features/obsidian-wiki).

In just one sync pass, the agent has full (compressed) context of your inbox, your calendar, your repos, your docs, your messages. No training period. No "give it a few weeks.". It becomes you, controlled by you.

Already self-host [agentmemory](https://github.com/rohitg00/agentmemory) across other coding agents? OpenHuman ships an optional `Memory` backend that proxies to it. Set `memory.backend = "agentmemory"` in `config.toml` and the same durable store powers OpenHuman alongside Claude Code, Cursor, Codex, and OpenCode. See the [agentmemory backend](https://tinyhumans.gitbook.io/openhuman/features/obsidian-wiki/agentmemory-backend) page for setup.

## An orchestrator, not a chatbot

Most agent harnesses run one agent in one loop. OpenHuman is an **[orchestrator](https://tinyhumans.gitbook.io/openhuman/features/orchestration)**:

<p align="center">
 <img src="./gitbooks/.gitbook/assets/orchestration.png" alt="OpenHuman orchestration diagram">
</p>

> Agent-to-agent messaging runs over Signal-protocol end-to-end encryption, so you can connect anything (Claude Code, Codex, OpenClaw, Hermes) and use OpenHuman to orchestrate all of your agents and tools.

- **Graphs, not loops**: turns run as checkpointed graphs on [tinyagents](https://github.com/tinyhumansai/tinyagents). They pause for a human, survive a restart, and resume mid-run.
- **Sub-agent fleets**: specialists spawn three levels deep; stuck agents become root-cause reports.
- **Agent-to-agent, encrypted**: instances orchestrate each other over Signal-protocol E2E sessions with x402 payments. No server ever sees plaintext.

Ask for an automation and it proposes one: a [tinyflows](https://github.com/tinyhumansai/tinyflows) graph you review on a visual canvas before saving.

## How to actually test whether a model runs

Rule of thumb for CPU-only inference: **you need roughly 1.3–1.5x the GGUF file size in free RAM**, and speed scales down roughly with model size and up with quantization level (Q4 > Q5 > Q8 for speed, opposite for quality). With 32GB free and no GPU competing for it:

- **4B models (Q4/Q5)** — comfortable, should be fast enough for real back-and-forth use. This is your daily driver tier.
- **8B–14B models (Q4)** — will run, noticeably slower per response (think 10-30s for a paragraph), fine for "ask and wait" tasks, bad for rapid iteration.
- **20B+ (Q4)** — will load and run on 32GB RAM but likely single-digit tokens/sec on this CPU — usable for something you kick off and check later, not chat.

Don't theorize past this — Jan's Hub shows a "fit" indicator per model/quant against your detected hardware before you download, and `jan serve <model> --fit` auto-fits context size to what you have. ## What Jan is actually for (and the gap you'll hit)

Jan is a **local model runner + chat client**, not a proactive assistant. Concretely, use it for:

- **Private daily chat/reasoning** against local models when you don't want data leaving the machine, or against cloud models (bring your own OpenAI/Anthropic/Groq key) through the same UI.
- **"Projects"** — the closest thing Jan has to memory: a project bundles conversations + uploaded files (PDF/MD/DOCX/code) as shared RAG context. Not automatic, not cross-project, but genuinely useful for scoping — e.g. a "Career Search" project with your resume/tracker uploaded, an "Obsidian Vault Dev" project with relevant notes.
- **MCP servers** — Settings → MCP Servers lets you wire in STDIO/HTTP/SSE tool servers directly (web search, filesystem access, code execution). This is how you give a Jan chat actual reach into your vault or the web, by hand.
- **Local OpenAI-compatible server** (`localhost:1337`, or `jan serve` at `localhost:6767`) — scriptable by anything else on your machine.
- **`jan launch claude`** — starts a local model and wires Claude Code to use it as the backend instead of Anthropic's API.

What it will never do on its own: watch your inbox, build a persistent cross-session memory of you, or run background agents. That's not a missing feature — the Jan team **deliberately removed** in-app agent orchestration in v0.7.9 "due to resource usage and security concerns." They're intentionally staying a model runner, not becoming OpenHuman.

### The Communication Flow

1. **JavaScript Layer Relationships**:
   - Web App imports Core SDK and Extensions as JavaScript modules
   - Extensions use Core SDK for shared functionality
   - All run in the browser/webview context

2. **All Three → Backend**: Through Tauri IPC
   - **Web App** → Backend: `await invoke('app_command', data)`
   - **Core SDK** → Backend: `await invoke('core_command', data)`
   - **Extensions** → Backend: `await invoke('ext_command', data)`
   - Each component can independently call backend commands

3. **Backend → Plugins**: Native Rust integration
   - Backend loads plugins as Rust libraries
   - Direct function calls, no IPC overhead

4. **Response Flow**:
   - Plugin → Backend → IPC → Requester (Web App/Core/Extension) → UI updates

### Real-World Example: Loading a Model

Here's what actually happens when you click "Download Llama 3":

1. **Web App** (`web-app/`) - User clicks download button
2. **Extension** (`extensions/download-extension`) - Handles the download logic
3. **Tauri Backend** (`src-tauri/`) - Actually downloads the file to disk
4. **Extension** (`extensions/llamacpp-extension`) - Prepares model for loading
5. **Tauri Plugin** (`src-tauri/plugins/llamacpp`) - Starts llama.cpp process
6. **Hardware Plugin** (`src-tauri/plugins/hardware`) - Detects GPU, optimizes settings
7. **Model ready!** - User can start chatting
