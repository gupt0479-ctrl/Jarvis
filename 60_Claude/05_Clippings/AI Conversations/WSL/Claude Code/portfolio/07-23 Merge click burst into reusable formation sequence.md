756-765) — since both clamps run and the tighter one always wins, the click can never push

## Bug #2 — why the connections look wrong, not just "close"

The planet edge list (`pEdges`, built once, lines 293-314) is a fixed nearest-neighbor graph
computed from REST positions only — never recomputed against live/scattered positions. Each
frame, an edge is either drawn full-length or collapsed to an invisible zero-length segment
based on a distance check against `effectiveMld2` (lines 782-813). But the intro's starting
threshold (4.4) is deliberately larger than almost any real scattered pairwise distance can
be — so at maximum scatter, essentially no edges get culled; nearly the whole ~3-edges-per-
point web stays "connected" the entire time, just invisible because the line material's
opacity (a single global value for the whole line buffer, lines 566-571) is near 0 early on.
As opacity ramps up and the threshold shrinks in parallel, what becomes visible is a hazy,
roughly-uniform web thinning out — not individual connections popping in one at a time as
specific point-pairs happen to reconverge close enough. That's the gap between what's there
and "barely connected to 2-3 nodes, then progressively connecting into a sphere." Fix it by
making the threshold do real culling work from frame one — start it much closer to the final
maxLineDist, not oversized — so only the pairs that land close by chance are visible early,
with more joining as convergence progresses. Connectivity and visibility should be driven by
the same signal, not opacity papering over a threshold that isn't culling anything yet.

## Performance test results — portfolio homepage (`/`)

**Bottom line:** the background (`ObsidianBackground`) is *not* the main offender — it's correctly lazy-loaded already. The real problem is that **three other things force the same heavy Three.js vendor code to load synchronously anyway**, defeating the background's own lazy-loading. ### 5 confirmed issues, ranked by impact

**1. Three.js loads on every visit because of the Education section, not the background — HIGH**
`EducationFlowchart.tsx` (`src/components/EducationFlowchart.tsx`) imports `@react-three/fiber`, `@react-three/drei`, and `three` directly at the top of a `"use client"` file, with no lazy-loading guard. It's statically imported into `EducationSection.tsx`, which is always rendered on `/`. I confirmed by curling the actual production HTML: the Three.js core + fiber chunk (`232 KB gzipped`) ships as a real `<script src>` tag on page load — even though this section is far below the fold and most visitors never scroll to it. `ObsidianBackground` and `Orby` both correctly use `dynamic(() => import(...), { ssr: false })`; this file is the one place that doesn't, and because it forces the shared Three.js vendor chunk in eagerly, it also silently defeats the other two components' lazy-loading (the vendor code is already loaded by the time they'd request it).
**Fix:** split it the same way `HeaderLogo.tsx` already does — move the R3F code into `EducationFlowchartCanvas.tsx` and wrap it: `const EducationFlowchart = dynamic(() => import("./EducationFlowchartCanvas"), { ssr: false })`.

**2. Clerk auth SDK loads on every page, including the public portfolio — MEDIUM**
`ClerkProvider` wraps the entire app in `src/app/layout.tsx`. Grepping for actual Clerk usage (`useUser`, `useAuth`, `SignedIn`, etc.) turns up only `src/app/studio/[[...tool]]/page.tsx` and the proxy/middleware — nothing in the public portfolio content. I confirmed ~188 KB of raw Clerk SDK code sits in the `/` route's eager bundle for a feature that only gates `/studio`.
**Fix:** move `ClerkProvider` down into the `/studio` and sign-in/sign-up layouts instead of the root layout, or lazy-load it behind those specific routes.

**3. GSAP (+ ScrollTrigger + SplitText) loads globally via `Providers.tsx` — MEDIUM**
`Providers.tsx` does a top-level `import gsap from "gsap"` plus `ScrollTrigger`, and `split-heading.tsx` additionally pulls in the `SplitText` plugin. Confirmed ~116 KB raw of GSAP code in the `/` route's eager bundle. Most of this drives scroll-triggered heading animations that aren't needed until each section scrolls into view.
**Fix:** import GSAP/plugins inside the components that use them (already client components) rather than in the app-wide `Providers`, or dynamic-import `SplitHeading`.

**4. Background canvas allocates on every mouse move — LOW (runtime, not bundle size)**
In `ObsidianBackgroundCanvas.tsx`, the `useFrame` loop is correctly zero-allocation (verified — no `new THREE.*` inside it), but the `pointermove` handler does `new THREE.Vector3(nx, ny, 0.5).unproject(camera)` on every single mouse-move event, uncapped by frame rate. On a high-poll-rate mouse/trackpad this creates real GC churn while the cursor moves over the hero.
**Fix:** hoist one reusable `THREE.Vector3` outside the handler and call `.set(...).unproject(camera)` on it instead of allocating a new one each time.

**5. The background's physics loop never throttles when it's scrolled out of visual relevance — LOW/MEDIUM**
The canvas only pauses on `document.hidden` (tab backgrounded). It has no check for whether the sphere is actually visible vs. fully obscured by the opaque `.cosmic-card` content stacked over it deep in the page — it runs the full per-frame particle physics (2800 planet points + up to ~8400 edges + ~2000 ring points, every frame) at full cost regardless of scroll position, burning CPU/GPU/battery even when nothing behind the cards is visible.
**Fix:** cheap scroll-based gate — skip (or heavily throttle) the physics update when `smoothScroll` places the viewport over a section where the background's `opacity`/coverage is near-zero; you already compute `stretchT`/`smoothScroll` every frame, so this is a few extra lines, not a new system.

Removing the forced-eager Three.js (232 KB gz), Clerk (~188 KB raw), and GSAP (~116 KB raw) from the initial bundle brings first-load JS for `/` down by roughly a third to a half, with the background's own lazy-loading finally doing what it was built to do.
